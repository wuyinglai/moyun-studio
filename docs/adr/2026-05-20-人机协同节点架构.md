# ADR: 人机协同节点架构

日期：2026-05-20

## 状态

Accepted

## 背景

墨韵已经具备工作流、Pipeline、文件操作和暂停恢复等基础能力。随着爽文模式和专业版同时演进，系统需要一个更统一的抽象，否则会出现两套创作逻辑：

- 爽文模式偏“动态创作、选卡、候选稿、故事引擎”
- 专业版偏“Prompt、Pipeline、工作流、文件管理”

如果二者长期分离，后续会出现重复实现、状态不一致、用户在两种模式切换时体验断裂等问题。

## 决策

采用三层架构作为后续统一模型：

```text
Workflow 工作流
  Chain 执行组
    Node 执行节点
```

第三层不再称为 Prompt，而统一称为 Node。Prompt 是节点类型之一。

正式节点类型包括：

- Prompt Node
- Human Node
- File Node
- Memory Node
- Quality Node
- Condition Node
- Retrieval Node
- Patch Node
- Version Node

人的互动被视为正式节点或作者意图输入，而不是备注。文件读写也作为正式节点暴露给专业版用户，便于自定义工作流。

所有高风险内容修改默认先生成候选稿或候选补丁，用户采用后才写入正式文件，并在采用后触发故事引擎与近期上下文更新。

## 后果

### 正向影响

- 专业版状态更清晰：每一步都能说明执行者、输入、输出和等待对象。
- 爽文模式和专业版可以共用底层能力。
- 作者可以在聊天、人工节点、候选稿三处自然介入创作。
- 长篇连续性更容易维护，因为记忆写入可以被审阅和追踪。
- 文件读写进入工作流后，用户自定义能力更完整。

### 成本

- 前端工作流编辑器需要从 Pipeline 视角升级为 Node 视角。
- 后端执行状态需要补充等待用户、候选稿、变量池、文件影响范围等契约。
- 旧工作流需要兼容映射：`pipeline` 映射为 Prompt/Chain 调用节点，`file` 映射为 File Node，`loop` 映射为 Loop/Condition 能力。

### 兼容策略

- 旧 YAML 工作流继续可运行。
- 前端展示时将旧 step 类型映射为新节点类型。
- 第一阶段只做状态和文档对齐，不强制迁移所有旧文件。
- 爽文模式保持简单界面，但内部逐步复用候选稿、记忆、质量节点。

## 不做的事

- 不把爽文模式改成复杂工作流编辑器。
- 不要求普通用户理解变量和节点。
- 不在第一阶段重写全部工作流引擎。
- 不把聊天输入直接自动写入正式文件。
