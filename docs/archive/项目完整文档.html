墨韵 (Moyun) - AI小说创作助手

墨韵是一个AI辅助小说创作平台，帮助作者管理小说项目的结构、角色、情节，并使用AI生成高质量的小说内容。

项目结构

  • backend/ - Python后端（FastAPI）
  • docs/ - 项目文档
  • workspace/ - 用户工作区（包含prompts模板）
  • setup_project.py - 项目初始化脚本

技术栈

  • 后端: Python 3.10+, FastAPI, LiteLLM, aiofiles
  • 前端: HTML/CSS/JavaScript (CDN引入)
  • AI: OpenAI GPT-4 / Claude / Ollama (通过LiteLLM统一调用)

快速开始

# 安装依赖
pip install -r requirements.txt

# 复制环境配置
cp .env.example .env
# 编辑 .env 填入你的 API Key

# 启动开发服务器
uvicorn backend.main:app --reload

墨韵 - 领域上下文

本文档定义墨韵项目的核心领域术语和概念。

核心领域术语

项目与结构

术语 定义
项目 (Project) 一个完整的小说创作项目，包含多个章节、角色和素材
章节 (Chapter) 小说的基本单位，包含正文和元数据
卷 (Volume) 章节的逻辑分组，用于组织长篇小说
工作区 (Workspace) 项目文件的根目录

Prompt系统

术语 定义
模板 (Template) Jinja2格式的Prompt模板文件
生成类模板 (Generate) 用于创建新内容的模板（书名、大纲、章节等）
提取类模板 (Extract) 用于从内容中提取信息的模板（角色、情节等）
转换类模板 (Transform) 用于修改现有内容的模板（润色、翻译等）
片段引用 (@{path}) 模板中引用其他文件内容的语法

质量保障

术语 定义
文风指南 (Style Guide) 定义写作风格、禁忌、样本文本
故事状态 (Story State) 当前故事进度、伏笔、阵营等
近期上下文 (Recent Context) 最近几章的摘要和统计
用户反馈 (Feedback) 用户对生成内容的反馈
修改日志 (Revision Log) 内容的修改历史

LLM交互

术语 定义
任务 (Task) 一次LLM调用请求，包含模板和变量
Token计数 使用tiktoken计算文本token数
流式输出 LLM的增量输出方式
重试机制 使用tenacity的指数退避策略

版本管理

术语 定义
快照 (Snapshot) 某一时间点的文件内容副本
对比 (Diff) 两个版本之间的差异

服务模块

术语 定义
LLM服务 (LLMService) 封装LiteLLM调用，提供流式输出和重试
文件服务 (FileService) 异步文件读写，支持frontmatter
Prompt引擎 (PromptEngine) 模板加载和渲染
任务队列 (TaskQueue) 管理异步生成任务
文件监听器 (FileWatcher) 监听文件系统变化，推送SSE事件

数据流

用户请求 → API路由 → Prompt引擎(渲染模板) → LLM服务(调用) → 文件服务(保存)
                                        ↓
                              Token计数(检查上下文)

墨韵 - AI 小说创作助手 产品说明

一、产品概述

1.1 产品名称

墨韵 - AI 小说创作助手

1.2 产品定位

一款面向中文小说创作者的AI辅助写作工具，通过AI技术帮助用户从零开始创作完整的小说作品。支持从项目创建、大纲生成、章节写作到内容润色的全流程自动化。

1.3 核心价值

  • 零门槛创作：用户只需选择创作参数，AI自动生成书名、大纲、章节内容
  • 灵活控制：支持L1半自动/L2连续两种自动化等级
  • 实时协作：通过SSE实时显示AI生成过程，随时干预调整
  • Prompt可视化：显示发送给AI的完整Prompt，透明可控

1.4 目标用户

  • 网文作者：快速产出内容，提高创作效率
  • 写作爱好者：降低创作门槛，体验AI辅助写作
  • 内容创作者：批量生成小说内容

三、核心功能流程

3.1 新建项目流程

1. 点击"新建"按钮
2. 弹出创建项目模态框
3. 选择创作参数（题材/基调/背景/主题/风格）
4. 选择作品规模（5万/10万/15万/20万字）
5. 点击"创建项目"
6. 进入三阶段引导流程：
   - 阶段1：AI生成书名+创意 → 用户确认/编辑
   - 阶段2：AI生成大纲（含卷/章/节结构） → 用户确认/编辑
   - 阶段3：自动生成目录结构，开始写作
7. 完成创建，打开项目

目录生成规则：
- 根据作品规模计算总节数：总字数 / 1800（每节约1800字）
- 章序号全局连续，每章固定4节
- 自动划分卷（通常8-15章一卷）
- 生成的三级目录结构：
chapters/ ├── vol-01/ │ ├── vol-meta.json │ ├── ch-001/ │ │ ├── ch-meta.json │ │ ├── sec-001.md │ │ ├── sec-002.md │ │ ├── sec-003.md │ │ └── sec-004.md │ └── ch-002/ └── vol-02/
- 同时生成 characters/、materials/extracted/、backup/ 目录

3.2 编辑器操作流程

1. 从文件树点击打开文件
2. 在编辑器中查看/编辑内容
3. 点击工具栏按钮触发AI操作：
   - 重写本文件：AI重新生成整个文件内容
   - 写下一部分：AI在文件末尾续写
4. 右侧面板实时显示Prompt
5. 执行面板显示任务进度
6. 完成后自动更新文件内容

3.3 AI对话流程

1. 在底部聊天输入框输入需求
2. 点击发送或按Enter
3. 消息显示在聊天区（用户消息靠右）
4. AI开始处理，显示"LLM调用中"
5. AI回复流式显示在聊天区（AI消息靠左）
6. 完成后隐藏"LLM调用中"状态

3.4 自动化等级

  • L1 半自动：默认模式，每步操作需要用户确认后，AI才执行下一步
  • L2 连续：AI自动连续执行，无需等待用户确认

二十、规则总结

  1. 目录即分类：Prompt 模板按 generate/extract/transform 分类，extract 下子目录由用户自由创建
  2. 模板结构：每个模板包含 main.md（内容）+ meta.json（元数据）+ blocks/（按需创建）
  3. 模板引用：使用 Jinja2 {% include 'blocks/xxx.md' %} 语法引用本模板的片段
  4. 章节结构：卷 > 章 > 节，章和节序号全局连续，每章固定4节
  5. 单文件存储：角色档案和提取结果都是每个对象单独一个文件
  6. 角色档案：characters/ 目录统一存储角色档案
  7. 提取结果存储：materials/extracted/{type}/ 存储提取结果，每个结果单独一个文件
  8. 版本管理：Prompt 和项目都有独立的快照机制
  9. 信息推断：ID 类信息从目录/文件名推断，不重复存储
  10. 文件生命周期：每类文件有明确的创建、更新、删除规则
  11. 约束限制：目录/文件名有严格的命名规范
  12. 异常处理：文件丢失、目录结构破坏等情况的处理方式已定义
  13. 新增质量保障：新增 style-guide.md、story-state.md、recent-context.md、feedback/、revision-log/ 等文件，提升生成质量
  14. Prompt 增强：章节撰写和续写模板新增多个引用变量，增强上下文感知能力

一、设计原则

1.1 RESTful 风格

  • GET：读取资源（不修改数据）
  • POST：创建资源 / 执行操作
  • PUT：完整更新资源
  • PATCH：部分更新资源
  • DELETE：删除资源

1.2 响应格式统一

所有接口返回统一结构：

{
  "success": true,
  "data": { ... },
  "message": "操作成功",
  "error": null
}

失败响应：

{
  "success": false,
  "data": null,
  "message": "文件不存在",
  "error": {
    "code": "FILE_NOT_FOUND",
    "details": "projects/demo/sec-001.md"
  }
}

1.3 状态码规范

HTTP状态码 说明 使用场景
200 OK 请求成功
400 Bad Request 参数错误
401 Unauthorized 未授权（未来扩展）
403 Forbidden 权限不足（未来扩展）
404 Not Found 资源不存在
409 Conflict 资源冲突（如重名）
422 Unprocessable Entity 业务逻辑错误

500 Internal Server Error 服务器错误
503 Service Unavailable LLM服务不可用

  • TaskExecutor: 删除后，任务执行逻辑分散到API层 → 深层 ✓
  • PromptEngine: 删除后，模板渲染逻辑需要重写 → 深层 ✓
  • snapshot.py: 删除后，快照功能消失但不影响核心 → 浅层

    def __init__(self, config: LLMConfig):
        self.config = config
        self.client = LiteLLMClient(config)

    async def complete(
        self,

        model: str | None = None,
        stream: bool = True
    ) -> AsyncGenerator[str, None]:
        """流式生成"""

        self,
        messages: list[dict],
        max_retries: int = 3

class PromptEngine:
    """Prompt模板引擎"""

    def __init__(self, prompts_path: Path, file_service: FileService):
        self.prompts_path = prompts_path  # workspace/prompts/
        self.file_service = file_service
        self.env = Jinja2Environment(
            loader=FileSystemLoader(str(prompts_path))
        )

    def load_template(self, category: str, template_type: str) -> Template:
        """加载模板"""
        template_path = f"{category}/{template_type}/main.md"
        return self.env.get_template(template_path)

    async def render(
        self,
        category: str,
        template_type: str,
        variables: dict[str, Any]
    ) -> str:
        """渲染模板"""
        template = self.load_template(category, template_type)

        # 解析片段引用 @{file_path}
        for key, value in variables.items():
            if isinstance(value, str) and value.startswith("@{"):
                variables[key] = await self._resolve_reference(value)

        return template.render(**variables)

    async def _resolve_reference(self, ref: str) -> str:
        """解析片段引用 @{file_path}"""
        file_path = ref[2:-1]  # 去掉 @{
        content, _ = await self.file_service.read_file(file_path)
        return content

# 伪代码示例
def render_prompt(template_name, context):
    # 1. 加载模板
    template = load_template(f"{template_name}/main.md")

    # 2. 收集变量（包含新增变量）
    variables = {
        "chapter_name": read_filename(context.chapter_id),

概述

本文档定义迭代循环开发模型，是整个项目的开发纲领。

核心理念：文档是活着的，不是一次写完就定稿的。每深入思考一步，相关文档都要同步更新，确保所有文档始终一致。

一、迭代循环模型（核心纲领）

1.1 核心理念

开发不是线性阶段，而是每个模块都走一遍完整的迭代循环：

┌───────────────────────────────────────────────┐
│                                               │
│   ┌─────────┐   ┌─────────┐   ┌─────────┐  │
│   │ 1.思考   │──>│ 2.文档   │──>│ 3.同步   │  │
│   │ 深化     │   │ 更新     │   │ 检查     │  │
│   └─────────┘   └─────────┘   └─────────┘  │
│                             │                │
│                             v                │
│   ┌─────────┐   ┌─────────┐   ┌─────────┐  │
│   │ 6.下一   │<──│ 5.验收   │<──│ 4.代码   │  │
│   │ 模块     │   │ 钩子     │   │ 实现     │  │
│   └─────────┘   └─────────┘   └─────────┘  │
│                                               │
└───────────────────────────────────────────────┘

1.2 六个迭代步骤

步骤1：思考深化

  • 深入理解当前模块的需求
  • 发现之前文档的不足或错误
  • 形成新的认知

步骤2：文档更新

  • 根据新认知，更新相关文档
  • 可能是《原型生成说明》，也可能是《功能清单》或《文件系统设计》
  • 每次只更新一个文档（避免混乱）

步骤3：同步检查（强制）

  • 根据"文档同步检查机制"，检查依赖当前文档的其他文档
  • 如果需要更新，先完成同步，再继续
  • 未完成同步检查，不得进入步骤4

步骤4：代码实现

  • 根据更新后的文档，实现代码
  • 遵循《功能清单》里的执行逻辑
  • Prompt必须独立存储，不得硬编码

步骤5：验收钩子（强制）

  • 对照《功能清单》逐项打勾
  • 使用搜索工具确认每项功能都有对应代码
  • 验收不通过，不得进入步骤6

步骤6：进入下一模块

  • 当前模块验收通过后，才能进入下一模块
  • 如果下一模块的发现需要修改前面文档，回到步骤1

1.3 核心原则

  1. 文档优先 - 所有代码实现前，先确认文档完备
  2. 契约驱动 - 功能清单、API契约 = 开发契约，契约不确认不动手
  3. Prompt独立 - Prompt必须独立存储，禁止硬编码在代码里
  4. 验收钩子 - 每个模块开发完成后，必须对照《功能清单》逐项打勾
  5. 文档同步 - 每次更新一个文档，必须检查所有依赖它的文档
  6. 追问到底 - "还有吗？"是口头禅
