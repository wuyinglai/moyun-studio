# 专业版节点化改造计划

本文用于指导专业版前端和后端的后续调整。目标不是推翻现有专业版，而是把已经存在的工作流、Pipeline、文件操作、暂停能力，整理成更清晰的节点模型。

## 一、现状判断

专业版已经具备三层架构的基础：

- Workflow：已有工作流编排和执行记录。
- Chain / Pipeline：已有多步 Prompt 管线。
- Step / Node 雏形：已有 pipeline、loop、file 等步骤类型。
- Pause / Resume 雏形：已有可暂停状态，但前端表达和节点语义不够统一。

主要问题不是“没有架构”，而是：

- 前端仍把 Prompt / Pipeline 当作核心对象，人的确认、文件读写、记忆更新没有统一成节点。
- 暂停状态没有明确表达“等待谁、等待什么、用户处理后产出哪个变量”。
- 作者意图更多停留在聊天或备注里，没有进入变量池、候选稿和工作流日志。
- 文件读写能力存在，但对用户来说不是一种可组合的正式节点。
- 质量审稿、记忆更新、候选稿采用还没有形成统一闭环。

## 二、改造目标

专业版前端要从“Prompt 管线编辑器”升级为“工作流节点工作台”。

核心目标：

- 第三层统一叫 Node，Prompt 是节点类型之一。
- 用户能看懂每个节点由谁执行：AI、系统、用户。
- 每次暂停都明确显示等待原因、输入内容、可选动作、输出变量。
- 文件读写、候选稿、记忆更新、质量审稿都能作为节点接入。
- 聊天表达的作者意图可以转化为候选改稿、变量、或节点输入。

## 三、前端页面调整

### 1. 工作流编辑器

将步骤类型从偏技术的 `pipeline / loop / file` 扩展为节点类型展示：

- Prompt 节点
- Human 节点
- File 节点
- Memory 节点
- Quality 节点
- Condition 节点
- Retrieval 节点
- Patch 节点
- Version 节点

第一版不必全部后端落地，但前端信息架构应预留。

### 2. 工作流运行面板

运行面板应展示：

- 当前工作流
- 当前节点
- 节点状态：等待执行、执行中、等待用户、已完成、失败、已跳过
- 当前输入
- 当前输出
- 产生或修改的变量
- 读取或写入的文件
- 下一步将进入哪个节点

当节点等待用户时，展示固定动作：

- 通过
- 编辑后通过
- 重新生成
- 插入补充要求
- 终止流程

### 3. 变量池面板

变量池不只是技术调试信息，而是作者控制故事的地方。建议分组显示：

- 用户输入变量：作者意图、风格、禁忌、偏好
- AI 输出变量：草稿、摘要、评分、候选方向
- 人工确认变量：final_ / approved_ 前缀内容
- 系统变量：项目、章节、路径、运行状态

后续节点默认使用 `final_` 或 `approved_` 变量，避免误用草稿。

### 4. 候选稿面板

专业版应比爽文模式展示更多信息：

- 候选稿来源节点
- 候选稿关联原文件
- 候选稿生成参数
- 与原文差异
- 采用后会触发的后续节点

候选稿动作：

- 采用
- 放弃
- 继续改
- 另存为素材
- 生成对比摘要

### 5. 对话框升级

对话框不是简单聊天窗口，而是作者意图入口。

用户输入后，系统应给出可确认动作：

- 修改当前文件
- 修改选中文件
- 影响下一场景生成
- 更新角色/设定/故事引擎
- 仅记录为创作备注

第一版可以只做“生成候选改稿”，后续再扩展为结构化意图。

## 四、后端契约调整

### 1. 节点统一结构

建议新节点结构包含：

```json
{
  "id": "review_memory_update",
  "name": "确认记忆更新",
  "type": "human_review",
  "executor": "human",
  "status": "waiting_for_user",
  "input": "{{steps.extract_memory.output}}",
  "output_key": "approved_memory_update",
  "actions": ["approve", "edit_and_approve", "regenerate", "stop"]
}
```

### 2. 暂停状态统一结构

```json
{
  "run_id": "run_001",
  "status": "waiting_for_user",
  "current_node": "review_memory_update",
  "waiting_reason": "请确认是否写入故事引擎",
  "input": "...",
  "actions": ["approve", "edit_and_approve", "regenerate", "stop"]
}
```

### 3. 文件节点扩展

File Node 不只做 mkdir/copy/delete，还应支持：

- read
- write
- append
- patch
- create_candidate
- adopt_candidate
- delete_candidate
- snapshot

## 五、迁移顺序

### P0：文档和术语对齐

- 明确 Workflow / Chain / Node。
- 明确 Human Node、File Node、Memory Node、Quality Node。
- 明确候选稿是所有高风险修改的统一机制。

### P1：前端运行状态清晰化

- 工作流运行面板显示“当前节点”和“等待对象”。
- 暂停状态统一成“等待用户处理”。
- 节点输出进入变量池。

### P2：候选稿和文件节点产品化

- 专业版加入候选稿列表、预览、采用、放弃。
- File Node 在编辑器里可视化配置。
- 采用候选稿后触发记忆更新。

### P3：人工节点落地

- 支持 human_review、human_edit、human_choice。
- 工作流运行到人工节点时暂停。
- 用户处理后恢复工作流。

### P4：记忆与质量节点落地

- Memory Node 支持人工确认写入。
- Quality Node 支持阈值判断和自动补强分支。
- Recent Context 与 Story Engine 更新时机可追踪。

### P5：对话入口结构化

- 聊天输入先转成作者意图。
- 作者选择作用范围。
- 系统生成候选改稿或更新变量。

## 六、验收标准

- 用户能在专业版看清楚工作流当前卡在哪个节点。
- 用户能知道一个暂停是在等人工确认、人工修改还是人工选择。
- 用户能看到每个节点读取了哪些文件、产出了哪些变量。
- 用户能用候选稿机制安全修改正文或设定。
- 用户采用候选稿后，故事引擎和近期上下文会在正确时机更新。
- 爽文模式和专业版共用同一套候选稿、记忆、质量和文件能力。
