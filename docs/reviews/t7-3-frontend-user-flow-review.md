# T7.3 前端用户流程 Review

## 1. 任务背景

T7.2 已正式收口，当前进入 T7.3：前端用户流程 review。

本阶段目标不是立即修改代码，而是从真实用户使用路径出发，系统检查 Moyun Studio 前端核心流程是否顺畅、清楚、可理解，重点关注用户在"创建项目 → 打开项目 → 生成下一场景 → 查看 candidate → preview / adopt / delete → 处理 warning / error"这一完整链路中的体验问题。

本次 review 结果将作为后续前端体验优化、错误提示完善、流程简化和回归验收的依据。

## 2. Review 范围

本次重点检查以下 8 个用户流程：

1. 新建项目流程
2. 打开项目流程
3. Professional 写下一场景
4. candidate 生成与展示
5. preview / adopt / delete
6. 连续性 warning 的前端呈现
7. dry-run / 真实 LLM 的区分
8. 错误提示是否足够清楚

## 3. Review 原则

本次 review 遵循以下原则：

1. **先不改代码**
   本阶段只记录问题、风险和改进建议，不直接进行代码修改。

2. **以普通用户视角检查**
   重点关注用户是否知道下一步该点哪里、当前发生了什么、出错后如何处理。

3. **优先发现阻断性问题**
   如果某个流程会导致用户无法继续使用，应标记为高优先级。

4. **区分功能问题和体验问题**
   功能问题指流程无法完成或结果错误；体验问题指可以完成但提示不清楚、状态不明显、操作成本高。

5. **为后续任务拆分做准备**
   本文档不直接提出大规模重构，只记录可被拆成后续小任务的问题。

## 5. 用户流程检查

### 5.1 新建项目流程

#### 预期流程

用户应能够从首页或项目入口顺利创建新项目，并理解以下信息：

* 项目名称
* 项目保存位置或项目标识
* 项目类型 / 模板
* 场景目标字数
* 章节 / 场景规划参数
* 创建成功后的跳转位置

#### 检查点

| 检查项 | 结果 | 备注 |
| --- | --- | --- |
| 是否能找到"新建项目"入口 | 待检查 | |
| 新建项目表单字段是否容易理解 | 待检查 | |
| 默认值是否合理 | 待检查 | |
| 必填项为空时是否有提示 | 待检查 | |
| 创建成功后是否明确进入项目 | 待检查 | |
| 创建失败时是否有清楚错误提示 | 待检查 | |

#### 初步关注点

* 如果字段过多，普通用户可能不知道哪些必须填、哪些可以保持默认。
* 如果"章节 / 场景 / 字数"概念同时出现，需要避免用户误解。
* 创建成功后应有明确反馈，不能让用户怀疑是否创建成功。

### 5.2 打开项目流程

#### 预期流程

用户应能够清楚地看到已有项目，并顺利打开目标项目。

#### 检查点

| 检查项 | 结果 | 备注 |
| --- | --- | --- |
| 是否能找到"打开项目"入口 | 待检查 | |
| 项目列表是否展示足够信息 | 待检查 | |
| 是否能区分不同项目 | 待检查 | |
| 打开项目后是否能看到当前项目状态 | 待检查 | |
| 项目不存在 / 加载失败时是否有提示 | 待检查 | |

#### 初步关注点

* 项目打开后，用户需要明确知道"当前正在编辑哪个项目"。
* 如果加载失败，不应只显示技术错误，应告诉用户可以怎么处理。
* 项目列表中建议展示项目名、最近修改时间、路径或摘要信息。

### 5.3 Professional 写下一场景

#### 预期流程

用户在 Professional 模式下，应能够基于当前上下文触发"写下一场景"能力，并生成候选内容。

#### 检查点

| 检查项 | 结果 | 备注 |
| --- | --- | --- |
| Professional 模式入口是否清楚 | 待检查 | |
| "写下一场景"按钮或操作是否容易理解 | 待检查 | |
| 点击后是否有 loading / task 状态 | 待检查 | |
| 生成过程中是否避免重复点击 | 待检查 | |
| 生成完成后是否明确出现 candidate | 待检查 | |
| 生成失败时是否说明原因 | 待检查 | |

#### 初步关注点

* 用户需要知道当前是在"生成候选稿"，而不是直接覆盖正文。
* 生成过程应有明确状态，例如"正在生成""已生成候选稿""生成失败"。
* 如果依赖上下文、story state、style guide 或 recent context，前端最好能在必要时给出轻量说明。

---

### 5.4 candidate 生成与展示

#### 预期流程

生成结果应作为 candidate 展示，而不是直接覆盖原文。

#### 检查点

| 检查项 | 结果 | 备注 |
| --- | --- | --- |
| candidate 是否能正常生成 | 待检查 | |
| candidate 是否展示在明确区域 | 待检查 | |
| 用户是否能区分正文与 candidate | 待检查 | |
| candidate 是否显示来源 / 类型 | 待检查 | |
| 多个 candidate 时是否容易区分 | 待检查 | |
| candidate 消失 / 刷新后状态是否合理 | 待检查 | |

#### 初步关注点

* candidate 必须和正文有明显视觉区分。
* 用户应能理解 candidate 是"待采纳内容"，不是已经写入正文。
* 如果有 task_id / project_id 过滤逻辑，前端需要避免展示其他项目或旧任务的 candidate。

---

### 5.5 preview / adopt / delete

#### 预期流程

用户应能够先预览 candidate，再决定是否采纳或删除。

#### 检查点

| 检查项 | 结果 | 备注 |
| --- | --- | --- |
| preview 入口是否清楚 | 待检查 | |
| preview 是否不会直接修改正文 | 待检查 | |
| adopt 前是否有明确确认或冲突检查 | 待检查 | |
| adopt 后正文是否正确更新 | 待检查 | |
| delete 是否只删除 candidate | 待检查 | |
| delete 后是否有状态反馈 | 待检查 | |

#### 初步关注点

* preview 应保持安全，不应产生写入副作用。
* adopt 是高风险操作，需要确保不会误覆盖用户已经编辑过的正文。
* delete 后应明确告诉用户 candidate 已删除，避免用户误以为正文被删。

---

### 5.6 连续性 warning 的前端呈现

#### 预期流程

当生成内容存在连续性风险时，前端应清楚展示 warning，并帮助用户判断是否继续 preview / adopt。

#### 检查点

| 检查项 | 结果 | 备注 |
| --- | --- | --- |
| warning 是否能正常显示 | 待检查 | |
| warning 文案是否能被普通用户理解 | 待检查 | |
| warning 是否区分严重程度 | 待检查 | |
| warning 是否影响 adopt 决策 | 待检查 | |
| warning 是否容易被忽略 | 待检查 | |

#### 初步关注点

* warning 不应只是技术字段展示，例如 continuity_warning=true。
* 建议使用用户能理解的表达，例如"可能与前文设定不一致""人物状态可能冲突"。
* 对严重 warning，adopt 前最好有二次确认或明显提示。

---

### 5.7 dry-run / 真实 LLM 的区分

#### 预期流程

用户应能清楚知道当前生成是 dry-run 模拟结果，还是真实 LLM 生成结果。

#### 检查点

| 检查项 | 结果 | 备注 |
| --- | --- | --- |
| dry-run 状态是否清楚展示 | 待检查 | |
| 真实 LLM 状态是否清楚展示 | 待检查 | |
| 用户是否能理解 dry-run 的含义 | 待检查 | |
| dry-run 结果是否避免被误认为正式生成 | 待检查 | |
| 切换模式后状态是否同步更新 | 待检查 | |

#### 初步关注点

* dry-run 是开发 / 测试语义，普通用户可能不理解。
* 如果面向内部开发版，可以保留 dry-run，但必须明显标记。
* 建议候选稿区域显示来源，例如"模拟生成结果"或"真实模型生成结果"。

---

### 5.8 错误提示是否足够清楚

#### 预期流程

当发生错误时，用户应知道：

1. 当前发生了什么问题
2. 是否影响当前正文
3. 是否可以重试
4. 是否需要检查配置
5. 是否需要查看日志或联系开发者

#### 检查点

| 检查项 | 结果 | 备注 |
| --- | --- | --- |
| 网络错误是否有提示 | 待检查 | |
| 后端错误是否有提示 | 待检查 | |
| LLM 配置错误是否有提示 | 待检查 | |
| 文件冲突是否有提示 | 待检查 | |
| adopt 失败是否有提示 | 待检查 | |
| 错误提示是否避免纯技术堆栈 | 待检查 | |

#### 初步关注点

* 错误提示不能只显示 "500 Internal Server Error"。
* 对用户可处理的问题，应给出下一步建议。
* 对开发者问题，可以保留错误码，但应附带普通语言解释。

## 6. 问题分级标准

本次 review 中发现的问题建议按以下等级记录：

| 等级 | 含义 | 示例 |
| --- | --- | --- |
| P0 | 阻断主流程，用户无法继续 | 无法创建项目、无法打开项目、生成后完全无结果 |
| P1 | 高风险，可能导致数据误改或用户严重困惑 | candidate 被误认为正文、adopt 覆盖用户修改 |
| P2 | 明显体验问题，但不阻断使用 | 文案不清楚、状态不明显、按钮位置不直观 |
| P3 | 后续优化项 | 视觉细节、轻量提示、布局微调 |

## 8. 初步结论

当前 T7.3 处于 review 准备阶段，尚未进入代码修改。

本阶段完成标准：

1. 完成 8 个核心用户流程检查
2. 明确记录发现的问题
3. 对问题进行 P0 / P1 / P2 / P3 分级
4. 判断是否存在阻断后续阶段的问题
5. 形成后续可拆分执行的小任务列表

如果本次 review 未发现 P0 / P1 阻断问题，则 T7.3 可以作为前端用户流程 review 文档阶段收口，并进入后续体验优化或具体问题修复阶段。

## 9. 后续建议

T7.3 完成后，建议根据 review 结果进入以下方向之一：

1. 若发现 P0 / P1 问题：优先安排修复任务，不进入新功能开发。
2. 若只发现 P2 / P3 问题：可整理为前端体验优化清单，分批处理。
3. 若主流程基本顺畅：可进入下一阶段，继续推进真实 LLM、长文本生成、候选稿管理或发布前体验打磨。
