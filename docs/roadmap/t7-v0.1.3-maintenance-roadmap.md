# T7：v0.1.3 维护版与可用性增强路线图

## 1. 阶段背景

Moyun Studio 已完成 v0.1.2 发布。

v0.1.2 的重点是产品化发布前整理，包括：

* 发布前 smoke checklist；
* known issues 分类；
* UI 文案相关 E2E 补跑；
* Release Notes；
* GitHub Release；
* 发布归档报告；
* T6.9.0 到 T6.10.4 阶段收口。

当前状态说明：

* v0.1.2 已正式发布；
* GitHub Release 已创建；
* v0.1.2 发布归档报告已完成；
* T6 产品化发布前体验整理阶段已全部完成；
* v0.1.2 tag 不应再移动；
* v0.1.2 GitHub Release 不应覆盖。

T7 阶段不以大功能开发为目标，而是进入 v0.1.3 维护版周期，重点提升启动体验、回归验证、用户流程清晰度、开发者体验和架构风险可控性。

---

## 2. 阶段定位

T7 阶段名称：

**T7：v0.1.3 维护版与可用性增强阶段**

阶段定位：

> 从“能发布”推进到“更容易启动、更容易验证、更不容易被 AI 改坏、更适合继续迭代”。

T7 不追求大而全的新功能，而是优先解决 v0.1.2 发布后最值得补强的维护项。

---

## 3. 阶段目标

T7 阶段主要目标如下：

1. 完成 v0.1.2 发布后的 smoke 回归；
2. 固化 post-release smoke 记录；
3. 改善开发启动体验；
4. 梳理 dev-check / dev-start 方案；
5. 梳理前端用户流程薄弱点；
6. 梳理后端结构风险；
7. 降低 Solo / AI 修改代码时的误改风险；
8. 为 v0.1.3 维护版准备 Release Notes 和发布流程。

T7 完成后，项目应达到：

* 新开发者更容易启动；
* 用户主流程更容易理解；
* 发布后验证更可重复；
* 已知风险更清晰；
* 下一版发布范围更可控。

### T7.1：发布后 smoke 回归与问题清单

目标：

验证 v0.1.2 发布后，main 分支仍然处于可用状态。

检查范围：

1. Git 状态；
2. main / origin/main / ls-remote 一致性；
3. v0.1.2 tag 不移动；
4. GitHub Release 可访问；
5. release-preflight 文档可执行；
6. 后端可启动；
7. 前端可 build；
8. UI 文案相关 E2E 可通过；
9. 默认不启用真实 LLM；
10. 不使用真实 API Key；
11. known issues 中无当前触发的 Release Blocker。

建议产出：

```text
docs/releases/v0.1.2-post-release-smoke.md
```

验收标准：

* post-release smoke 有记录；
* 当前无阻断发布后使用的问题；
* 若发现问题，必须区分 blocking / non-blocking；
* 不修改 v0.1.2 tag；
* 不覆盖 GitHub Release。

---

### T7.2：启动体验与 dev-check 脚本整理

目标：

改善开发者和用户的本地启动体验，降低启动失败概率。

重点问题：

* 后端怎么启动；
* 前端怎么启动；
* 端口 8000 / 5173 被占用怎么办；
* 如何确认真实 LLM 没有启用；
* 如何确认没有使用真实 API Key；
* 如何确认依赖安装完整；
* 如何定位常见启动失败。

建议产出：

```text
docs/dev-start.md
scripts/dev-check.ps1
```

可选产出：

```text
scripts/dev-start.ps1
```

`dev-check.ps1` 建议检查：

1. Python 是否可用；
2. Node 是否可用；
3. npm 是否可用；
4. backend 目录是否存在；
5. frontend 目录是否存在；
6. 端口 8000 是否占用；
7. 端口 5173 是否占用；
8. LLM smoke 环境变量是否为空；
9. 是否存在明显 API Key / token 泄露风险；
10. Playwright 产物是否误留在工作区。

验收标准：

* dev-check 可复制执行；
* 检查结果清晰；
* 不调用真实 LLM；
* 不使用真实 API Key；
* 不做 installer；
* 不改业务代码。

---

### T7.3：前端用户流程 review

目标：

梳理 v0.1.2 当前前端用户流程中容易误解、容易卡住、容易误操作的点。

检查范围：

1. 新建项目流程；
2. 打开项目流程；
3. 场景 / 文件选择流程；
4. Professional dry-run 入口；
5. candidate 生成后的展示；
6. candidate preview；
7. adopt / delete 行为；
8. adopt 前冲突提示；
9. 不自动覆盖正文的提示；
10. 错误提示是否足够“人话”；
11. 用户是否知道当前是 dry-run 还是真实 LLM。

建议产出：

```text
docs/ux/t7-frontend-flow-review.md
```

验收标准：

* 有明确问题清单；
* 每个问题区分严重程度；
* 每个问题给出最小改进建议；
* 不直接大改 UI；
* 不引入新交互复杂度。

---

### T7.4：后端结构风险 review

目标：

梳理后端当前结构中可能影响后续维护的风险，形成最小重构计划。

关注范围：

1. `main.py` 职责是否过重；
2. `app.state` 依赖是否难以测试；
3. Pipeline / Workflow / Prompt Engine 边界是否清楚；
4. Story State / Materials / Style Guide / Recent Context 是否仍有接口不统一；
5. FileService 路径安全是否有回归风险；
6. API contract 是否需要进一步集中；
7. SSE / Task Queue / Candidate 事件契约是否清晰；
8. 哪些地方不适合 Solo 一次性大改。

建议产出：

```text
docs/architecture/t7-backend-risk-review.md
```

验收标准：

* 只做 review，不直接大重构；
* 每个风险都给出影响范围；
* 每个风险都给出最小修复策略；
* 明确哪些区域禁止一次性重构；
* 为后续 T7.x 或 T8 拆任务。

---

## 6. 优先级分类

P0 是 T7 最小闭环，建议必须完成：

1. T7.0 阶段规划；
2. T7.1 发布后 smoke 回归；

7. v0.1.3 发布前最终检查。

---

### P1：应该做

P1 建议在 T7 中尽量完成：

1. 前端用户流程 review；
2. 后端结构风险 review；
3. README / 启动文档补强；
4. release-preflight 与 dev-check 的关系说明；
5. 常见错误排查说明；
6. Windows PowerShell 使用说明。

---

### P2：可延后

P2 可以放到后续版本，不建议阻塞 v0.1.3：

1. 大规模 UI 改版；
2. 多模型管理；
3. 真实 LLM 生产级接入；
4. 插件系统；
5. 多项目工作区管理；
6. 更复杂的任务队列 UI；
7. 自动更新机制。

---

### 暂不做

以下内容 T7 阶段不做：

1. 大规模架构重写；
2. 云端部署平台；
3. 多人协作权限系统；
4. 复杂账号体系；
5. 数据库迁移；
6. 付费系统；
7. 大规模插件市场；
8. 完整生产级 LLM 网关；
9. 大范围替换前端技术栈；
10. 一次性重构 Pipeline / Workflow / Prompt Engine 全部链路。

## 7. 风险控制

T7 阶段必须遵守以下规则：

1. 每个任务开始前必须确认 Git 状态；
2. 每个任务结束后必须确认工作区 clean；
3. 涉及代码改动必须运行对应 build / test；
4. 文档任务不得混入代码改动；
5. 不移动已发布 tag；
6. 不覆盖 GitHub Release；
7. 不启用真实 LLM，除非任务明确要求；
8. 不使用真实 API Key；
9. 不提交 `.env`；
10. 不提交 token / secret；
11. 不提交 Playwright trace / screenshot / video 等测试产物；
12. 不提交临时文件；
13. 不让 Solo 一次性做大范围重构；
14. 每次 Solo 完成后必须进行二次独立验收。
