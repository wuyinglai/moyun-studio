# T7.3 前端用户流程 Review

## 1. 任务背景

T7.2 已正式收口，当前进入 T7.3：前端用户流程 review。

本阶段目标不是立即修改代码，而是从真实用户使用路径出发，系统检查 Moyun Studio 前端核心流程是否顺畅、清楚、可理解，重点关注用户在"创建项目 → 打开项目 → 生成下一场景 → 查看 candidate → preview / adopt / delete → 处理 warning / error"这一完整链路中的体验问题。

本次 review 结果将作为后续前端体验优化、错误提示完善、流程简化和回归验收的依据。

## 2. Review 范围

本次重点检查以下 8 个用户流程：

1. 新建项目流程
2. 打开项目流程
3. Professional 写下一场景
4. candidate 生成与展示
5. preview / adopt / delete
6. 连续性 warning 的前端呈现
7. dry-run / 真实 LLM 的区分
8. 错误提示是否足够清楚

## 3. Review 原则

本次 review 遵循以下原则：

1. **先不改代码**
   本阶段只记录问题、风险和改进建议，不直接进行代码修改。

2. **以普通用户视角检查**
   重点关注用户是否知道下一步该点哪里、当前发生了什么、出错后如何处理。

3. **优先发现阻断性问题**
   如果某个流程会导致用户无法继续使用，应标记为高优先级。

4. **区分功能问题和体验问题**
   功能问题指流程无法完成或结果错误；体验问题指可以完成但提示不清楚、状态不明显、操作成本高。

5. **为后续任务拆分做准备**
   本文档不直接提出大规模重构，只记录可被拆成后续小任务的问题。

| 检查项 | 结果 | 备注 |
| --- | --- | --- |
| preview 入口是否清楚 | ✅ 通过 | 每张卡片有眼睛图标按钮，hover tooltip "预览" |
| preview 是否不会直接修改正文 | ✅ 通过 | `previewContent` 是只读 textarea，预览弹窗 footer 明确写"预览只用于查看内容，不会修改正文" |

| adopt 后正文是否正确更新 | ✅ 通过（流程层面） | 依赖 `candidate.adopted` SSE 事件，CandidatePanel 有监听；需要再验证编辑器是否在 adopt 完成后同步 reload file |
| delete 是否只删除 candidate | ✅ 通过 | `deleteCandidate` 走后端 candidate 删除接口，不会触及源文件内容 |
| delete 后是否有状态反馈 | ⚠️ P3 | `notification` 有调用，但未验证文案是否友好；若用户误删 candidate，没有"已删除 / 可恢复"之类的提示 |

#### 关键观察
- **adopt 缺少前端二次确认**。若源文件在 candidate 生成后被用户手工编辑过，后端即使返回冲突，前端也需要一个清楚、可撤销的交互，而不是只展示一个技术错误。

### 5.8 错误提示是否足够清楚

#### 实际检查结果

| 检查项 | 结果 | 备注 |
| --- | --- | --- |
| 网络错误是否有提示 | ⏭ 未覆盖 | 本次未断开连接 |
| 后端错误是否有提示 | ⚠️ P2 | 浏览器测试中观察到"未找到元素 / Y 坐标 14745 超出视图"这样的纯技术报错是自动化层产物；对真实用户而言，需要验证 Vue 全局 ErrorBoundary 是否会把 500 / 解析异常翻译为可读提示 |
| LLM 配置错误是否有提示 | ⚠️ P2 | 若 LLM provider 配置缺失，现有流程可能仅在日志中出现失败，用户只会看到"生成失败"或按钮状态停留在"停止"，不清楚是 API key 问题、模型配置问题还是网络问题 |
| 文件冲突是否有提示 | ⚠️ P1 | 见 5.5；adopt 时的 FILE_CONFLICT 需要在前端以"你的正文已被修改，要先看看差异吗？"之类的文案呈现，而不是仅显示错误码 |
| adopt 失败是否有提示 | ⚠️ P2 | 未验证 adopt 失败的用户反馈流程；只从代码看依赖 notification store 的通用 success / error |
| 错误提示是否避免纯技术堆栈 | ⚠️ P2 | grep 到部分 `dry_run=${isDryRun}` 等开发者风格文案会直接出现在 notification 中；对普通用户不友好 |

#### 关键观察
- 候选稿 tab 底部没有"正在生成？""已生成但未采纳？""刚才生成失败了吗？"之类的轻量状态徽章。用户需要在 8 个 tab 间来回找信息，状态管理学习成本高。
- "continuity warning" + "file conflict" + "adopt 二次确认" 三者当前是独立甚至缺失的逻辑，建议统一成一个"候选稿健康状态徽章"。

## 6. 本次发现的问题清单（按优先级）

### 问题编号：T7.3-FE-001

| 项目 | 内容 |
| --- | --- |
| 流程位置 | Professional 写下一场景 → candidate 生成与展示 |
| 问题等级 | P1 |
| 问题描述 | "写下一场景" 写入正文后并未同步到候选稿 tab，用户在 editor 中直接看到生成内容，无法清晰区分"这是正式写入还是待采纳的候选稿" |
| 复现步骤 | 1. 打开任意项目 → 2. 点击顶部"📄 写下一场景" → 3. 等待生成完成 → 4. 切到"📝 候选稿"tab，发现为空或只有老数据 |
| 预期表现 | 高风险场景写入应首先走 candidate，生成完成后右侧候选稿 tab 有高亮、有 unread 徽标，并明确标注"待采用" |

| 建议处理 | 所有 `write_scene` 对已有内容 / 空场景以外的路径均先写入 candidate，adopt 前强制二次确认；新建场景时如果场景已存在内容，也应走 candidate |
| 是否阻断 T7.3 收口 | 否，但属于 T7.3+ 必须优先处理的 P1 |
